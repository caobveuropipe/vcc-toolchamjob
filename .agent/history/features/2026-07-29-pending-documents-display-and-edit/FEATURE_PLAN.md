- Forward SQL Migration `045_add_upload_status_to_employee_documents.sql`:
  - Bổ sung cột `upload_status` (`DEFAULT 'ready'`, `NOT NULL`), `expires_at`, `client_attempt_id` và `r2_cleanup_failed` cho `employee_documents`. Tạo partial unique index `idx_employee_docs_attempt` trên `(created_by, client_attempt_id) WHERE client_attempt_id IS NOT NULL`. Thực thi backfill `UPDATE employee_documents SET upload_status = 'ready' WHERE upload_status IS NULL;` (EFR-46, EFR-49, EFR-64, EFR-67).
  - <!-- Sửa theo EFR-74: Tạo bảng cleanup outbox, EFR-79: Cài đặt RLS bảo vệ bảng outbox queue --> Tạo bảng `r2_cleanup_queue` (id UUID PRIMARY KEY, r2_object_key TEXT UNIQUE NOT NULL, created_at TIMESTAMPTZ DEFAULT now()) để lưu trữ outbox queue cho các tài liệu bị xóa. Bật Row Level Security (RLS) cho `r2_cleanup_queue`, thiết lập policy deny direct-access `USING (false) WITH CHECK (false)`, thực hiện `REVOKE ALL ON TABLE r2_cleanup_queue FROM PUBLIC, anon, authenticated` để chỉ cho phép backend service role quản trị.
  - <!-- Sửa theo EFR-80, EFR-82, EFR-83, EFR-89, EFR-90, EFR-91, EFR-94, EFR-95, EFR-96, EFR-97, EFR-99, EFR-100, EFR-101, EFR-102, EFR-103, EFR-104, EFR-105, EFR-109, EFR-110: Cơ chế Lazy Sweep dọn dẹp an toàn, lock DB thống nhất, RLS hardening, function timeout và CLI drain --> Thiết lập cơ chế chạy tự động dọn dẹp (Garbage Collection):
    - **Cơ chế Tự Kích Hoạt Cơ Hội (Opportunistic Lazy Sweep - EFR-89, EFR-91)**: Tích hợp hàm dọn dẹp `runLazySweepCleanup(limit = 5, bypassThrottle = false)` vào các mutating API endpoints (Presign, Finalize, Delete). Bắt buộc phải `await` quá trình dọn dẹp này trong request lifetime (EFR-89).
      * *Failure Isolation (EFR-94)*: Lệnh dọn dẹp sweep phải chạy trong khối `try/catch` độc lập đứng SAU khi nghiệp vụ chính đã hoàn tất/commit. Bất kỳ lỗi mạng, lỗi DB, hay timeout nào từ cleanup sweep đều được log lại bằng `logger.error` và **tuyệt đối không được thay đổi kết quả response/status code của API chính** (Primary Response Wins).
      * *Bounded Elapsed Budget & Timeout Cancellation (EFR-95, EFR-101, EFR-105, EFR-109, EFR-111)*: Đảm bảo thời gian chạy tối đa 2 giây (wall-clock deadline) (EFR-107). Tại mỗi bước của sweep (DB batch RPC -> S3 Delete -> DB acknowledge), tính toán thời gian còn lại (remaining budget). Sử dụng `AbortSignal.timeout(remainingBudget)` truyền vào các S3 client commands (EFR-95) và các options của Supabase JS client requests (EFR-109) để Node hủy request HTTP nếu hết hạn. Để đồng thời bảo vệ server-side transaction khỏi việc chạy ngầm (detached DB processing - EFR-111), **tất cả các cleanup SQL RPCs đều nhận tham số `p_timeout_ms INT`** (hoặc `p_deadline_at`) và gọi lệnh dynamic config `PERFORM set_config('statement_timeout', LEAST(p_timeout_ms, 2000)::text, true);` ở ngay đầu transaction (EFR-111). Điều này đảm bảo PostgreSQL tự động hủy transaction và rollback hoàn toàn nếu truy vấn vượt quá quỹ thời gian còn lại (remaining budget) thực tế. Giới hạn xử lý tối đa `LIMIT 5` records mỗi đợt quét.
      * *Crash-safe Read-only Batch & Acknowledge-only Mutation (EFR-108, EFR-110)*: Để đảm bảo an toàn tuyệt đối khi Node process bị crash/chết đột ngột giữa các bước dọn dẹp (EFR-108, EFR-110), các hàm SQL RPC lấy lô dọn dẹp (`fn_cleanup_expired_documents_batch` và `fn_cleanup_outbox_queue_batch`) hoạt động **thuần Read-only (chỉ SELECT các bản ghi eligible, không xóa/sửa đổi trạng thái trước khi gọi R2)**. Mọi thao tác ghi dữ liệu (UPDATE status sang `failed` / delete outbox row) chỉ được thực thi atomically ở bước cuối cùng sau khi có kết quả xóa từ S3 thông qua hàm `fn_acknowledge_cleanup_results` (EFR-110). Nếu quá trình bị gián đoạn trước bước Acknowledge, dữ liệu vẫn ở trạng thái an toàn và sẽ được quét lại ở lượt tiếp theo.
    - **Cơ chế Tiết Kiệm Tải & Lease Lock DB Thống Nhất (EFR-90, EFR-96, EFR-99, EFR-100)**: Chỉ thực sự quét dọn dẹp nếu khoảng cách giữa 2 lần quét tối thiểu là 15 phút.
      * *DB làm Authority duy nhất (EFR-99)*: Để tránh lỗi split-brain khi Redis và DB hoạt động độc lập (EFR-99), **DB RPC `fn_try_claim_cleanup_sweep` là nguồn chân lý duy nhất quyết định quyền quét**. Redis chỉ đóng vai trò tùy chọn làm cache pre-filter ở backend (nếu có key `cron:last_cleanup_run` thì skip ngay để giảm tải DB).
      * *Database Hardening & Bounded Claim Timeout (EFR-96, EFR-100, EFR-112)*: Tạo bảng `cleanup_state` (id INT PRIMARY KEY DEFAULT 1, last_run_at TIMESTAMPTZ NOT NULL, CONSTRAINT single_row CHECK (id = 1)) với RLS deny-all (`USING (false) WITH CHECK (false)`) và `REVOKE ALL ON TABLE cleanup_state FROM PUBLIC, anon, authenticated`. Tạo hàm RPC `fn_try_claim_cleanup_sweep(p_interval_seconds INT, p_timeout_ms INT) RETURNS BOOLEAN` định nghĩa với `SECURITY DEFINER SET search_path = public`, thực hiện `PERFORM set_config('statement_timeout', LEAST(p_timeout_ms, 2000)::text, true);` (EFR-112) rồi mới thực thi update atomic `UPDATE cleanup_state SET last_run_at = NOW() WHERE last_run_at < NOW() - (p_interval_seconds * INTERVAL '1 second')`. Lệnh gọi RPC từ client ở Node cũng được ghim abort signal timeout để tự ngắt (EFR-112). Đồng thời thực hiện `REVOKE EXECUTE ON FUNCTION fn_try_claim_cleanup_sweep FROM PUBLIC, anon, authenticated` và `GRANT EXECUTE ON FUNCTION fn_try_claim_cleanup_sweep TO service_role` (EFR-100).
    - **Quy trình Vận Hành Ops Fallback & CLI Drain (EFR-91, EFR-97, EFR-102, EFR-104)**: Lập tài liệu vận hành cho DevOps khi hàng đợi outbox bị dồn ứ (nếu không có traffic upload/delete trong thời gian dài).
      * *Cadence/Query (EFR-104)*: Kiểm tra hàng ngày qua câu query tính oldest pending age trên union của cả outbox queue và expired/failed documents:

## 3. Đối chiếu Knowledge Base

- **Quyết định kế thừa:**
  - Dual-payload Pending Save & `temp_uuid`: Giữ nguyên nguyên tắc `_temp_uuid` kết nối giữa bản ghi `pending_changes` và các dòng trong `employee_documents`.
  - State-driven Visibility Isolation: Chỉ nhân sự có `state_phong_cho = true` hoặc có `pending_changes` mới nạp danh sách `pending-documents`.
  - UI Architecture: Sử dụng Ant Design v6 components (Card, List, Button, Popover, Typography, App message/modal) và Ant Icons.
  - Traceability & Audit: Mọi hành vi xóa chứng từ (phá hủy dữ liệu) phải được ghi vết vào Audit Trail (`recordAuditLogStrict`).
- **"Cấm kỵ" cần tránh:**
  - Tuyệt đối KHÔNG unmount thẻ `<Upload>` trong `DocumentUpload.tsx` khi đang tải (theo contract của file `DocumentUpload.tsx`).
  - Không sửa trực tiếp các file SQL Migration lịch sử cũ (EFR-48).
  - Tuyệt đối KHÔNG thực thi DB mutation hay cleanup trong API GET `getPendingDocuments` (phải 100% READ-ONLY) (EFR-28, EFR-33, EFR-52).
  - Không bỏ qua kiểm tra quyền actor TRƯỚC TIÊN khi Finalize API được gọi bằng `documentId` (EFR-65).
  - Không cho phép thiếu `document_type` khi gọi presign (bắt buộc scalar enum non-optional Zod validation) (EFR-66, EFR-72, EFR-76).
  - Không gọi advisory lock ở TypeScript client rồi thực hiện SQL query ở transaction riêng (bắt buộc dùng SQL RPC `reserve_document_upload`) (EFR-56).
  - Không cho phép client gửi `r2_object_key` tự chọn khi finalize (bắt buộc dùng `documentId` để load immutable key từ DB) (EFR-57, EFR-60).
  - Không finalize trạng thái `'ready'` nếu `HeadObject.ContentLength` vượt 5MB, S3 trả lỗi 404, hoặc <!-- Sửa theo EFR-77: so sánh khớp registered size_bytes --> `ContentLength` thực tế lệch so với đăng ký `size_bytes` (EFR-50, EFR-58, EFR-77).
  - Không trả lỗi 409/410 khi retry finalize bản ghi đã `'ready'` (bắt buộc trả 200 OK idempotent) (EFR-61).
  - Không map nhầm lỗi S3 5xx/Timeout thành 400 Bad Request (phải map sang 502/503 để client retry) (EFR-55).
  - Không truyền array `document_type` vào payload presign/save metadata (`uploadDocumentType` phải là scalar enum) (EFR-10, EFR-76).
  - Không nạp hoặc tính các bản ghi `upload_status = 'reserved'` vào UI và Submit evidence (EFR-46).
  - Không cho phép gọi trực tiếp SQL RPC (reserve hoặc delete) từ `anon` / `authenticated` role (bắt buộc `GRANT EXECUTE TO service_role`) (EFR-45, EFR-75).
  - Không cho phép Reviewer thực hiện bất kỳ thao tác ghi/xóa tài liệu nào, kể cả qua Presign và Finalize (Reviewer chỉ được xem/tải) (EFR-73).
